# Expense Tracker web

The responsive web client uses Next.js App Router, React, TypeScript, Tailwind CSS, Radix UI, TanStack Query, React Hook Form, Zod, and Recharts. It replaces the former Vue frontend and uses the existing Scala API.

The interface takes inspiration from Revolut's clear financial hierarchy: prominent amounts, quiet rounded surfaces, account filters, quick actions, and readable transaction lists. It keeps Expense Tracker's own identity and terminology.

## Run locally

Use Node.js 24 and npm. From this directory:

```sh
npm ci
cp .env.example .env.local
npm run dev
```

Open [localhost:3000](http://localhost:3000). The example environment connects to the hosted core service. For a separately configured local backend, change its origin to `http://localhost:6000`.

If `EXPENSE_TRACKER_CORE_URL` is unset, the app uses [the hosted core service](https://api--expense-tracker-core--j6xvqz9kpswd.code.run). That service is not a demo: signed-in actions affect the account's real data.

### Environment

| Variable                   | Purpose                                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `EXPENSE_TRACKER_CORE_URL` | Server-only HTTP(S) origin of the Scala service. Omit `/api`, paths, credentials, query strings, and fragments. `/api` is appended by the proxy. |
| `PORT`                     | HTTP listening port; the standalone container defaults to `3000`.                                                                                |
| `HOSTNAME`                 | Standalone server bind address; the container uses `0.0.0.0`.                                                                                    |
| `NEXT_TELEMETRY_DISABLED`  | Set to `1` to disable Next.js telemetry; already set in the container and CI.                                                                    |

Keep `.env.local` out of version control. The browser calls same-origin `/api/*` routes and never needs the core URL or a `NEXT_PUBLIC_*` backend variable. The backend origin is read at server runtime, so the same image can run against different core services.

## Feature scope

- Overview and analytics with account, currency, and date controls.
- Transaction browsing and filtering; single-amount creation, editing, copying, soft archive, and an immediate Undo action. Forms retain their values after failed saves; an uncertain creation requires checking the transaction list before retrying.
- Daily, weekly, and monthly recurring schedules with interval and date controls, previews, editing, and stopping future occurrences while keeping generated history. End dates are exclusive. The core generates due occurrences, including missed dates; the browser does not create recurring ledger entries itself.
- Account and category creation, editing, and soft archive. Archiving either also hides its assigned transactions and stops its recurring schedules. Account and category archive cannot be undone from the web app.
- Sign-in, registration, profile preferences, password changes, logout, clearing financial data, and closing the user account. Data clearing waits for the core to acknowledge cleanup and keeps the sign-in; account closure removes it after cleanup succeeds.
- Light, dark, and system appearance; a desktop sidebar and phone navigation.

Amounts describe recorded income, expenses, and net activity. They are not bank balances. Totals stay within the selected currency; the app does not perform exchange-rate conversion, connect banks, initiate payments, or add investment products.

Account currency is fixed when the account is created. Transaction and recurring forms start with the account selector and accept one amount with its currency symbol inside the field. New entries use their account's currency, or the profile's default currency for **No account**. Currency cannot be selected in these forms; existing entries keep their original currency when edited. Comma or Enter turns a tag into a removable pill, and category choices include their icons.

Overview, Transactions, and Recurring show individual visible accounts and use the selected account's currency, with no separate currency selector. The main account is selected by default, or the first visible account if no main account is available. If there are no visible accounts, **No Account** is the only option and shows unassigned entries in the profile's default currency. Saved links with an unavailable account fall back to the same defaults, and old currency filters are ignored. Entries in other currencies remain stored and are excluded from the selected currency's totals. The account selector fills the content width on phones.

This web client requires a connection. The mobile app and its offline database are unchanged. A known mobile compatibility limitation remains: its transaction and recurring editors save `accountId: null` and use the user's current default currency, including when editing an existing entry. Editing a web-created entry there can therefore remove its account assignment or change its currency. The web editors preserve existing assignments, currency, and recurrence metadata unless explicitly changed.

Mobile sync does not carry deletion tombstones: clearing data on the web does not clear another device's offline database, and pending mobile edits can reintroduce records. The current mobile client may therefore retain data after a web clear. Fixing that sync behavior is outside this release.

## Release order

Release the updated core before this frontend. The web experience depends on the accompanying backend fixes: registration waits for default account/category setup; financial-data clearing acknowledges completion across recurring schedules, transactions, categories, and accounts; account closure deletes the user only after that cleanup; and recurring generation catches up missed occurrences, saves them before advancing schedule checkpoints, and uses stable occurrence identifiers when retrying.

Run the backend checks and deploy that core revision first, then build and release the frontend against its origin. A previous core can still expose the same routes while retaining the earlier setup, cleanup, and recurrence behavior. This repository's checks do not deploy either service.

## Code layout

```text
src/app/                 Pages, shared layouts, API and health routes
src/components/          Shared controls, dialogs, states, and navigation
src/features/            Domain types, API hooks, and feature interfaces
src/lib/                 Dates, money formatting, ledger queries, API client
src/lib/server/bff.ts     Testable server-to-core proxy and cookie boundary
public/                  Original static assets
```

The browser sends credentials to `/api/auth/login`. The server exchanges them for a core bearer token and stores it in an `HttpOnly`, `SameSite=Lax`, session cookie. Production cookies also use `Secure`, so production access must use HTTPS. Successful login returns `204` with no token body. Registration returns the new user id; the client then signs in.

Financial query caches are scoped to the signed-in user and cleared on session changes. Sign-in and sign-out in another browser tab refresh the session and clear stale financial data in the current tab.

The API boundary:

- Allows explicit controller paths and HTTP methods; it is not an open proxy.
- Sends only JSON content headers and the session bearer token upstream.
- Requires same-origin requests for every mutation, including login and registration.
- Limits request bodies to 64 KB and core requests to 15 seconds, with no write retries.
- Uses private, non-cacheable responses and does not forward upstream cookies or redirects.
- Converts core authentication failures (`403`) into `401` with `code: "SESSION_EXPIRED"`, and clears the cookie.
- Preserves invalid-login and incorrect-current-password `401` responses as form errors without ending a valid session.
- Invalidates the core session on logout and clears the local cookie even if the core is unavailable. A failed upstream logout cannot confirm remote invalidation.
- Clears the cookie after successful password changes and account deletion. Deleting account data keeps the session.

The proxy and client do not log passwords, bearer tokens, cookies, or financial request bodies. Keep those values out of application logs, analytics, screenshots, and test artifacts. Automated tests use synthetic fixtures; do not substitute real credentials or enable request-body logging.

Core API boundaries matter: account detail `GET`, recurring detail `GET`, and recurring `DELETE` are not implemented controller routes. Sync endpoints are for the mobile client and are not exposed by the web proxy. Only transaction list requests accept `from` and `to` query parameters.

## Container

From the repository root:

```sh
docker build -t expense-tracker-web:local modules/frontend
docker run --rm -p 3000:3000 \
  -e EXPENSE_TRACKER_CORE_URL=http://host.docker.internal:6000 \
  expense-tracker-web:local
```

`host.docker.internal` works with Docker Desktop; use the appropriate reachable backend hostname on other hosts. The image uses Node.js 24 Alpine, runs as a non-root user, and includes only Next.js standalone output, static files, and public assets. Runtime configuration is not baked into the image.

Production cookies require HTTPS. Put TLS termination in front of the container and preserve the browser-facing `Host` and protocol. The origin check deliberately ignores `X-Forwarded-Host`; proxies must preserve `Host`. Direct HTTP access is suitable for checking pages and `/health`; use the development server for an HTTP sign-in session.

`GET /health` returns `{"status":"ok"}` when the frontend process responds. It performs no backend requests or authentication and is used for container and Kubernetes liveness/readiness checks.

The repository's [Compose file](../../docker-compose.yml) maps frontend port `8000` to container port `3000`. Its backend environment is retained from the existing setup: the current core expects `MONGO_USER`, `MONGO_PASSWORD`, and `MONGO_HOST` for an SRV connection, while the Compose backend still supplies `MONGO_CONNECTION_URI`. Configure the core appropriately before treating that Compose setup as a working local full stack.

The [Kubernetes frontend manifest](../../deployment/frontend.yaml) targets port `3000`, checks `/health`, and sets memory requests/limits of `128Mi`/`512Mi`. Deployment is a separate action; builds and tests do not publish images or apply manifests.
